# 六类产出文档的结构模板

成文阶段查阅本文件。每类文档按以下结构组织，长度由模块复杂度决定。

## 证据行写法

每段正文下面空一行，写一行证据：

```
blk-mq 把请求分发到每个硬件队列的软件队列，映射关系在分配时确定。

> 证据：[VERIFY: block/blk-mq.c:2380] [VERIFY: block/blk-mq.c:2412]
```

一条 `[VERIFY:]` 标签写一个位置，一行内可并列多条。正文句子里不写文件名和行号，出处只出现在证据行。图和表同样在下方补证据行，图内标签只写组件名。

## 1. 系统概述（System Overview）

- 项目目标与背景
- 核心模块清单与职责
- 技术栈与框架

## 2. 总体框架（Overall Framework）

- 分层结构图（PlantUML），标出各层的边界
- 核心组件清单：每个组件说明它为什么存在、负责什么
- 组件间的调用关系图与数据关系图，两张分开画
- 组件与关系的源码位置写在图下方和清单各条目的证据行

## 3. 数据结构/类详解（Data Structures）

- 结构体/类间的关系图(PlantUML)
- 关键结构体/类清单
- 每个结构体的字段说明、用途、生命周期
- 每个结构体所在段落的证据行指向其定义位置

## 4. 数据流分析（Data Flow）

- 数据流图
- 数据入口与出口
- 数据在各模块间的传递路径
- 每个变换点的输入输出说明
- 每个步骤所在段落的证据行标出该步骤的代码位置

## 5. 调用流程（Call Flow）

- 关键调用的入口与出口
- 函数间的调用关系图(PlantUML)
- 调用顺序与参数传递路径
- 每个调用步骤所在段落的证据行标出调用点

## 6. 典型场景分析（Typical Scenarios）

- 选择 3～5 个最有代表性的使用场景
- 每个场景按：场景目标 → 触发条件 → 执行路径 → 数据变化 → 结果展开
- 用场景验证架构能否解释真实问题
- 每个场景的执行路径分段给证据行

## 成文检查

- [ ] 成文前调用 rigorous-tech-writing skill，按其正文契约和禁用项逐条检查改写；它的"结论标注源码位置（文件:行号）"一条不适用于本 skill，源码位置一律写在段落下方证据行
- [ ] 每段重要结论下方都有证据行，覆盖该段全部结论
- [ ] 正文句子里没有源码位置和行号
- [ ] 运行 `scripts/verify_refs.sh` 输出"全部通过"
- [ ] 架构图、数据流图、调用图分开画，未合并
- [ ] 文档语言为中文，术语首次出现用一句话解释
