# 代码库分析

## 目标

对指定的代码库或模块做系统性分析，产出技术分析文档，包含：系统概述、总体框架、数据结构(类)分析、数据流分析、调用流程分析、典型场景分析。每段结论下方用证据行标出源码位置，没读过代码不许写结论，成文后必须复核。

## 核心规则

1. 源码优先。每段正文下面紧跟一行证据 `> 证据：[VERIFY: 相对路径/文件:行] [VERIFY: 相对路径/文件:行]`，一条标签写一个位置，段内每个结论都要能被证据覆盖。正文句子里不写文件名和行号，出处集中在证据行。未读代码不许下结论，不确定就删除内容。
2. 读代码 → 草稿 → 核验 → 修正 → 成文。执行核验步骤必须调用 `scripts/verify_refs.sh`，不得凭印象判断标签有效。
3. 调用流和数据流分开描述，不混淆。
4. 分析范围按"模块 → 主流程 → 核心组件 → 关键调用 → 源码细节"收敛，只分析与当前问题相关的代码。
5. 文档长度由模块复杂度决定，不设固定行数目标。

## 分析流程

1. **读取项目上下文**：检查被分析项目内是否存在 AGENTS.md/QODER.md/README.md，存在则读取作为上下文；不存在则直接从代码结构开始，不自动生成任何文件。检查点：能说出项目类型和主要语言。
2. **全局探索**：识别项目结构、关键模块、依赖关系、框架和架构。检查点：能指出每个模块对应的源码文件。
3. **分析规划**：列出要分析的模块清单，按复杂度或重要性排序，确定文档的产出顺序和覆盖范围。检查点：每个识别出的模块都有对应的文档计划。
4. **总体框架分析**：梳理系统的分层结构、核心组件、组件间的调用与数据关系，输出总体架构图和模块清单。检查点：图中每个组件都有对应的源码位置。
5. **数据结构分析**：枚举关键数据结构，记录字段、方法、关系，画结构图。检查点：每个结构所在段落都有 `[VERIFY:]` 标签指向实际定义。
6. **数据流分析**：沿代码执行路径追踪数据移动，记录每个阶段的输入输出和变换点。检查点：所有流程步骤可追溯到代码。
7. **调用流程分析**：梳理关键调用的执行路径，记录函数间的调用关系、调用顺序、参数传递。检查点：每条调用链都有代码证据。
8. **典型场景分析**：选择 3～5 个最有代表性的使用场景，按场景目标 → 触发条件 → 执行路径 → 数据变化 → 结果展开，用场景验证架构能否解释真实问题。检查点：每个场景都能追溯到源码。
9. **复核**：运行 `scripts/verify_refs.sh <文档路径> <代码库根目录>` 核验证据行里的所有 `[VERIFY:]` 标签，脚本逐条确认文件路径和行号真实存在；未通过的条目逐条修正，无法确认就删除该条内容；成文前对照 `references/doc-templates.md` 自检。检查点：脚本输出"全部通过"。

## 不要做的事

- 不要引用不存在的文件或行号。

- 不要未读代码就下结论。

- 不要把推测写成事实。

- 不要混淆调用流和数据流。

- 不要为了图好看增加不存在的组件或调用关系。

- 不要把每句话拆成单独一行，正文用正常技术文档分段。

- 不要把源码位置和行号写进正文句子，它们属于段落下方的证据行。

## Gotchas

- 引用不存在的文件行号：代码重构后行号变化，写入报告前必须重新核对源码，不能凭记忆。

- 把推测写成事实：未读代码就写"X 调用 Y"，如果实际没有调用关系，报告就失真。写入前先 grep 或读源码确认。

- 调研发散：从主流程滑进几十个类的细节后收不回来。每次进入源码前先写明当前要回答的问题，得到答案即返回主流程。

- （沉淀占位：实际运行中发现新的坑写在这里，收录标准是"不写这条，默认行为是否会出错"。）
